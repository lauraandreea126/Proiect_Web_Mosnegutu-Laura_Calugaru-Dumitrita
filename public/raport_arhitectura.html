1. Introducere

1.1 Contextul și Justificarea Proiectului

În ecosistemul web actual, analiza și vizualizarea volumelor mari de date culturale—în special cele legate de industria cinematografică și de galele de premiere (cum sunt premiile Screen Actors Guild - SAG)—sunt adesea dependente de platforme comerciale masive sau de framework-uri monolitice. Proiectul AwA (Actor Awards Visualizer) a fost conceput ca o soluție alternativă, de înaltă performanță, dedicată procesării, structurării și randării vectoriale a datelor istorice de premiere. Scopul principal este transformarea unor seturi de date brute (fișiere CSV de mari dimensiuni) în reprezentări grafice interactive, ușor de digerat de către utilizatorii finali.

1.2 Filosofia Designului: Zero Frameworks și Native Web Stack

O decizie arhitecturală fundamentală în dezvoltarea sistemului AwA o reprezintă excluderea completă a framework-urilor de frontend (cum ar fi React, Vue sau Angular) și de backend (precum Laravel sau Symfony). Această abordare de tip Vanilla sau Native Web Stack oferă avantaje tehnice incontestabile:

  • Absența Overhead-ului de Bootstrapping: Aplicația nu încarcă sute de megabyți de dependențe din directoare de tip node_modules sau module vendor, ceea ce garantează un timp de încărcare inițial (First Contentful Paint) extrem de redus, sub pragul critic de 300ms.
  • Securitate și Auditabilitate: Prin eliminarea bibliotecilor terțe, suprafața de atac cibernetic este redusă la minimum. Nu există riscul introducerii de vulnerabilități prin dependențe compromise (supply-chain attacks). Fiecare linie de cod din aplicație este scrisă nativ și poate fi auditată direct.
  • Sustenabilitate pe Termen Lung: API-urile native ale browserelor (Fetch API, DOM Manipulation) și standardele PHP core sunt stabile de ani de zile. Aplicația va continua să ruleze perfect fără a necesita mentenanță din cauza unor actualizări de versiuni de framework-uri care introduc modificări distructive (breaking changes).

Logica de business este distribuită modular: backend-ul acționează ca un motor de procesare pur, lăsând randarea vizuală în sarcina procesorului clientului prin utilizarea eficientă a limbajelor PHP 8 și JavaScript modern.

2. Modelarea Datelor și Persistența

2.1 Alegerea SQLite 3 ca Mediu de Stocare Embedded

Pentru gestionarea persistenței, s-a optat pentru sistemul de gestiune a bazelor de date relaționale SQLite 3, localizat fizic în directorul securizat data/awa.db. Spre deosebire de arhitecturile tradiționale client-server (precum MySQL sau PostgreSQL), SQLite este un motor de bază de date „embedded” (încorporat). Această decizie aduce avantaje critice în contextul proiectului:

  • Performanță la Citire (Zero Network Latency): Deoarece SQLite rulează în același proces cu interpretorul PHP și citește direct dintr-un fișier de pe disc, latența de rețea generată de sockets sau conexiuni TCP/IP spre un server de bază de date extern este egală cu zero. Acest lucru este ideal pentru operațiunile intense de citire necesare generării statisticilor.
  • Portabilitate Absolută și Zero Configuration: Întreaga bază de date este stocată într-un singur fișier compact. Aplicația devine complet portabilă: poate fi copiată pe orice mașină gazdă (cu server Apache/XAMPP) și va rula instantaneu, fără a fi necesară crearea de utilizatori, configurarea de privilegii sau rularea manuală de scripturi grele de import SQL.

2.2 Schema Detaliată a Tabelelor și Tipurile de Date

Schema bazei de date a fost normalizată conform regulilor formale (3NF) pentru a elimina redundanțele și a asigura integritatea referențială prin utilizarea constrângerilor de chei străine (FOREIGN KEY). Mai jos este prezentată structura detaliată a fiecărei tabele, incluzând constrângerile la nivel de coloană:

A. Tabela users (Gestiunea Securizată a Conturilor)

Stochează identitățile digitale pentru administratori și clienți. Parolele sunt stocate obligatoriu sub formă de hash-uri ireversibile.

  • id (INTEGER, PRIMARY KEY, AUTOINCREMENT): Identificatorul unic al utilizatorului.
  • username (VARCHAR(50), UNIQUE, NOT NULL): Numele de utilizator folosit la autentificare; indexat automat pentru căutare rapidă.
  • password_hash (VARCHAR(255), NOT NULL): Hash-ul generat prin algoritmul securizat BCRYPT.
  • rol (VARCHAR(20), NOT NULL): Definește privilegiile contului în sistem, având valorile stricte: 'admin' sau 'client'.
  • data_crearii (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP): Momentul înregistrării contului.

B. Tabela nominations (Depozitul Istoric de Date)

Această tabelă conține setul masiv de date brute utilizat pentru calculele matematice și statistice.

  • id (INTEGER, PRIMARY KEY, AUTOINCREMENT): Identificatorul nominalizării.
  • an (INTEGER, NOT NULL): Anul în care a avut loc gala de premiere (folosit intens în clauzele de filtrare WHERE și grupare GROUP BY).
  • categorie (VARCHAR(255), NOT NULL): Categoria premiului (ex: "Outstanding Performance by a Male Actor in a Leading Role").
  • nominalizat (VARCHAR(255), NOT NULL): Numele actorului sau grupului nominalizat. S-a aplicat un index pe această coloană pentru a optimiza viteza interogărilor statistice.
  • productie (VARCHAR(255), NOT NULL): Titlul filmului sau al producției cinematografice asociate.
  • castigator (INTEGER, NOT NULL, DEFAULT 0): Flag boolean (0 = nominalizat, 1 = câștigător), esențial pentru calcularea ratelor de succes în frontend.

C. Tabela actors (Subsistemul de Cache pentru Metadate API)

Funcționează ca un buffer local de tip Cache pentru a limita apelurile repetitive către API-ul extern TMDb, prevenind blocarea cheii API (rate-limiting).

  • id (INTEGER, PRIMARY KEY, AUTOINCREMENT): Identificatorul local.
  • tmdb_id (INTEGER, UNIQUE, NOT NULL): Identificatorul unic din baza de date externă TMDb, folosit ca punct de legătură la sincronizare.
  • nume (VARCHAR(255), NOT NULL): Numele complet al actorului.
  • biografie (TEXT): Textul biografic complet returnat de API.
  • imagine_url (VARCHAR(500)): Calea relativă sau URL-ul absolut către imaginea de profil a actorului.
  • data_actualizarii (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP): Data ultimei sincronizări cu API-ul extern.

D. Tabela favorites (Interacțiune și Monitorizare Consum)

Reprezintă o tabelă de joncțiune ce materializează relația de tip Many-to-Many între utilizatori (clienți) și actori.

  • id (INTEGER, PRIMARY KEY, AUTOINCREMENT): Identificatorul legăturii.
  • user_id (INTEGER, NOT NULL): Cheie străină (FOREIGN KEY) corelată cu users(id); la ștergerea utilizatorului, înregistrarea se elimină automat (ON DELETE CASCADE).
  • actor_id (INTEGER, NOT NULL): Cheie străină corelată cu actors(id) (ON DELETE CASCADE).
  • adaugat_la (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP): Data la care clientul a marcat actorul ca favorit. Permite administratorului să realizeze analize cronologice privind interesul publicului.

E. Tabela news_sources (Configurația Agregatorului RSS)

Stochează fluxurile de date XML pe care sistemul backend le va parsa asincron pentru a extrage știri proaspete.

  • id (INTEGER, PRIMARY KEY, AUTOINCREMENT): Identificatorul sursei.
  • nume_sursa (VARCHAR(100), NOT NULL): Numele lizibil al publicației (ex: "Google News - Cinema", "Hollywood Reporter").
  • url_xml (VARCHAR(500), UNIQUE, NOT NULL): URL-ul absolut către fișierul XML/RSS de unde se preiau datele text.
  • stare (INTEGER, DEFAULT 1): Flag pentru activare/dezactivare rapidă din panoul de admin (1 = Activ, 0 = Inactiv).

2.3 Gestiunea Tranzacțiilor SQL la Importuri Masive

Atunci când administratorul încarcă un fișier CSV ce conține mii de rânduri cu nominalizări istorice prin scriptul import_data.php, performanța brută a bazei SQLite ar colapsa dacă fiecare rând ar fi inserat individual (deoarece SQLite execută implicit un I/O write pe disc pentru fiecare comandă). Pentru a evita acest lucru, sistemul dezactivează auto-commit-ul și folosește explicit **Tranzacții SQL Atomice**:

$pdo->beginTransaction();
... buclă de parsare linii CSV și execuție Prepared Statements ...
$pdo->commit();

Această abordare grupează toate inserțiile într-o singură operațiune majoră de scriere pe disc, crescând viteza de import de la câteva zeci de rânduri pe secundă la peste 20.000 de rânduri pe secundă. În plus, garantează principiul **ACID**: dacă fișierul CSV este corupt la rândul 500, întreaga tranzacție dă înapoi ($pdo->rollBack();), prevenind poluarea bazei cu date parțiale sau incomplete.

3. Arhitectura Sistemului, Rutele REST API și Subsistemul de Notificări

Aplicația AwA folosește un model decuplat de tip RESTful API. Comunicarea se face exclusiv asincron prin obiecte JSON transmise prin rețea.

3.1 Logica de Cookie-uri și Securitatea Sesiunii Client

Sistemul nu folosește mecanisme stateless grele, ci recurge la sesiuni securizate native din PHP gestionate prin cookie-uri standard. La autentificarea cu succes prin /login.php, serverul instanțiază o sesiune și trimite în browser cookie-ul PHPSESSID. Acesta este configurat cu flag-urile de securitate obligatorii: HttpOnly (previne citirea cookie-ului prin scripturi JS malițioase, blocând atacurile XSS) și SameSite=Strict (previne atacurile de tip CSRF). Modulul frontend app.js verifică prezența acestui cookie la fiecare încărcare prin apelarea asincronă a endpoint-ului check_session.php pentru a deschide opțiunile dedicate clienților.

3.2 Arhitectura Tehnică a Sistemului de Notificări

Sistemul de notificări funcționează printr-o logică mixtă Frontend-Backend. Mesajele tranzacționale și erorile de sistem sunt interceptate de un manager de evenimente în JavaScript (app.js). La fiecare apel de API (cum ar fi adăugarea la favoriți, ștergerea unui cont de către admin sau un import eșuat), backend-ul PHP trimite un răspuns JSON structurat ce conține un câmp dedicat statusului și un mesaj explicit: {status: "success", message: "Notificare text"}. Frontend-ul interceptează acest obiect, creează dinamic un element HTML de tip "Toast alert" cu animații CSS transition și îl elimină automat din DOM după 4 secunde.

3.3 Selecție de Endpoint-uri ale API-ului REST

Următorul tabel detaliază toate rutele din spatele aplicației, inclusiv cele de management clienți și știri:

Metodă HTTP Endpoint API (Fișier PHP) Comportament detaliat în fundal și Declanșare Notificări
GET /api/check_session.php Analizează cookie-ul de sesiune primit; returnează starea utilizatorului (vizitator/client autentificat/admin) pentru modificarea interfeței.
POST /login.php Prelucrează datele introduse; compară hash-ul parolei; generează sesiunea și cookie-ul securizat sau trimite înapoi o notificare de eroare.
GET /api/search_actors.php Interoghează cache-ul din tabela actors și apelează API-ul extern TMDb prin cURL dacă înregistrarea lipsește.
GET /api/get_stats.php Efectuează operații matematice și agregate SQL (COUNT, SUM) direct în SQLite pentru a trimite seturile necesare graficelor SVG.
POST / DELETE /api/favorites_manager.php Inserează sau șterge o legătură în tabela favorites. Declanșează o alertă toast asincronă pe ecranul clientului.
POST /import_data.php Verifică sesiunea de admin, parsează fișierul CSV încărcat și execută inserții atomice folosind tranzacții SQL securizate.
GET /export_csv.php Generare dinamică și formatare în timp real de fișiere CSV descărcabile din tabelele de sistem.
GET / POST / DELETE /api/manage_clients.php Permite administratorului să auditeze, listeze și să elimine complet conturile clienților din sistem, oferind opțiunea de export JSON/CSV.

3.4 Diagramele de Arhitectură (Modelul C4)

Nivelul 1: Diagrama de Context

Sistemul AwA interacționează cu două tipuri de actori umani (Vizitator și Admin) și trei sisteme externe: TMDb API pentru biografii, Google News pentru știri specifice și diverse servere RSS pentru fluxuri generale.

Nivelul 2: Diagrama de Containere

Aplicația este divizată în trei containere principale: Web Browser (Frontend asincron), Server Web PHP (REST API) și Baza de Date locală SQLite.

Nivelul 3: Diagrama de Componente

În interiorul subsistemului PHP, componentele sunt izolate logic pe module: securitate, procesare statistici, gestionare catalog și management clienți, fiecare interacționând cu tabele distincte.

4. Strategii de Securitate și Imunizare

4.1 Filosofia „Security by Design” și Principiul Privilegiilor Minime

Securitatea sistemului AwA nu a fost tratată ca o adăugire ulterioară dezvoltării (afterthought), ci a fost integrată direct în faza de proiectare arhitecturală („Security by Design”). Având în vedere utilizarea unui stack tehnologic nativ, fără framework-uri care să ofere straturi automate de abstractizare și filtrare, întreaga logică de imunizare structurală a fost implementată manual, adresând direct vulnerabilitățile critice identificate în ghidurile internaționale OWASP Top 10.

4.2 Imunizarea împotriva Injecțiilor SQL (SQLi) la Nivel de Persistență

Atacurile de tip SQL Injection exploatează vulnerabilitățile în care datele introduse de utilizator sunt interpretate eronat de către interpretorul SQL ca fiind comenzi sau instrucțiuni executabile. În cadrul sistemului AwA, această vulnerabilitate este complet eliminată prin utilizarea exclusivă a obiectului PDO (PHP Data Objects) configurat cu mecanismul Prepared Statements (Interogări Parametrizate).

Procesul de securizare structurală se desfășoară în doi pași distincți la nivelul serverului de bază de date SQLite 3:

  1. Pre-compilarea și Separarea Logicii (PDO::prepare()): Structura SQL a interogării este trimisă către motorul bazei de date cu parametri de substituție (placeholders de tip :nominalizat sau :user_id). Motorul compilează planul de execuție exclusiv pe baza acestui șablon rigid, înainte ca datele utilizatorului să atingă serverul.
  2. Legarea Securizată a Valorilor (PDOStatement::bindValue()): Valorile transmise din frontend (prin cereri Fetch asincrone) sunt legate separat de structura gata compilată. Interpretorul bazei de date tratează aceste intrări strict ca valori literale (string-uri sau numere). Chiar dacă un atacator introduce caractere speciale de control (cum ar fi ' OR '1'='1), acestea vor fi stocate sau căutate ca text chior, făcând modificarea intenționată a interogării imposibilă din punct de vedere matematic. Nicio variabilă de intrare nu este concatenată direct în șirul SQL.

4.3 Strategii de Neutralizare a Atacurilor Cross-Site Scripting (XSS)

Vulnerabilitățile de tip XSS apar atunci când o aplicație web preia date nesigure din surse externe și le injectează direct în structura DOM a browserului, permițând rularea de scripturi JavaScript malițioase în contextul sesiunii utilizatorului curent. Deoarece AwA consumă date asincrone dintr-o multitudine de medii externe volatile (metadate și biografii din API-ul TMDb, fluxuri XML din serverele RSS), s-a implementat o strategie duală de igienizare:

  • Imunizare la Nivel de Backend (PHP-Side): Înainte de a trimite orice răspuns direct către client, textul este trecut prin funcția nativă htmlspecialchars() configurată cu flag-ul ENT_QUOTES. Acest proces convertește caracterele speciale de control HTML (<, >, &, ", ') în entitățile lor inofensive corespunzătoare (cum ar fi &lt; sau &gt;). Astfel, orice tag de tip <script> trimis malițios este neutralizat înainte de a părăsi serverul.
  • Imunizare la Nivel de Frontend (JavaScript-Side): În cadrul modulelor search_v2.js și `news.js`, se interzice cu strictețe utilizarea proprietății vulnerabile .innerHTML pentru injectarea textelor venite din API. În schimb, manipularea DOM-ului se face exclusiv prin proprietatea nativă .textContent. Aceasta forțează browserul să trateze string-ul primit pur ca pe un text literal afișabil, ignorând complet încercările de interpretare a tagurilor HTML sau a handlerelor de evenimente (ex: onload, onerror).

4.4 Managementul Criptografic al Parolelor și Securitatea Sesiunii

Platforma refuză stocarea parolelor în clar sau sub formă de hash-uri simple care pot fi sparte prin atacuri cu tabele pre-calculate (rainbow tables). Sistemul utilizează o implementare criptografică bazată pe algoritmul BCRYPT, invocat nativ prin password_hash(). Acest algoritm integrează automat o cheie unică de salt (salt) generată aleatoriu pentru fiecare utilizator și folosește un factor de cost computațional ajustabil. Acest lucru înseamnă că spargerea parolei prin tehnici de brute-force necesită resurse hardware nerealist de mari, garantând confidențialitatea datelor clienților.

Securitatea sesiunilor este întărită prin configurarea strictă a cookie-ului de sesiune PHPSESSID. Acesta este trimis către browser cu atributele HttpOnly (care blochează accesul scripturilor JavaScript la identificatorul de sesiune, stopând furtul de cont în caz de atac XSS stocat) și SameSite=Strict (care interzice trimiterea cookie-ului în cereri pornite de pe site-uri terțe, anulând complet riscul atacurilor Cross-Site Request Forgery - CSRF).

5. Motorul de Vizualizare SVG

5.1 Justificarea Vectorială: SVG versus Canvas

O decizie critică în proiectarea modulului de analiză vizuală a fost alegerea tehnologiei de randare grafică. Spre deosebire de soluțiile bazate pe elementul HTML5 <canvas>, care generează o matrice fixă de pixeli rasterizați (dependenți de rezoluție și predispuși la blurare la zoom), motorul de randare AwA generează elemente native SVG (Scalable Vector Graphics).

Fiind o structură bazată pe un dialect XML, fiecare formă geometrică din diagramă devine un nod real în arborele DOM al browserului. Acest lucru permite stilizarea elementelor grafice (bare, cercuri, arcuri de cerc) direct prin reguli CSS standard, manipularea lor individuală prin evenimente JavaScript (ex: afișarea unui tooltip dinamic la evenimentul mouseenter pe o anumită bară) și scalabilitatea infinită a imaginii, păstrând o claritate matematică perfectă pe orice ecran, indiferent de densitatea pixelilor (Retina/4K).

5.2 Algoritmul Matematic de Generare și Injectare DOM

Procesul de transformare a datelor statistice în obiecte geometrice se desfășoară asincron în frontend, prin modulul charts.js, urmând o pipeline matematică riguroasă formată din patru etape consecutive:

  1. Preluarea și Structurarea Datelor (Ingestion): Modulul JS trimite o cerere asincronă către get_stats.php și primește un set structurat JSON ce conține agregatele brute calculate în SQLite (ex: numărul de nominalizări, numărul de victorii, ratele procentuale de câștig ale actorului selectat).
  2. Calcularea Coordonatelor și Maparea Spațială: JavaScript determină dimensiunile geometrice reale (lățime, înălțime, raze polare) în funcție de dimensiunile elementului HTML container părinte (asigurând un comportament complet responsive). Pentru graficele de tip Plăcintă (Pie) sau Gogoașă (Donut), sistemul convertește valorile procentuale brute în radiani și folosește funcțiile trigonometrice Math.sin() și Math.cos() pentru a determina coordonatele carteziene de start și de final ale fiecărui segment de arc.
  3. Generarea Șirului XML Geometric: Se construiește programatic șirul de caractere XML corespunzător formelor dorite. Pentru diagramele cu bare se generează tag-uri <rect> cu atribute de poziționare explicite (x, y, width, height), iar pentru segmentele circulare complexe se generează elemente de tip <path> care folosesc comenzi avansate de desenare vectorială (d="M startX startY A raza raza ... L endX endY Z").
  4. Injectarea Dinamică în DOM (Rendering): Șirul XML rezultat este convertit în noduri DOM prin utilizarea metodei securizate document.createElementNS() (specificând spațiul de nume oficial SVG http://www.w3.org/2000/svg) și injectat în pagină, deblocând imediat interactivitatea și stilizarea CSS.

5.3 Tehnica de Rasterizare „Blitting” pentru Exportul WebP

Deși formatul SVG este ideal pentru afișare, utilizatorii au adesea nevoie să descarce graficele sub formă de imagini standard pentru a le include în documente externe. Pentru a asigura acest export în formatul modern WebP (care oferă o compresie net superioară formatelor vechi PNG sau JPG), fără a trimite datele înapoi la server, motorul implementează o tehnică avansată de tip "blitting" pe client:

  • Pasul A: JavaScript extrage întregul cod XML din elementul SVG din pagină, îl serializează și îl convertește într-un string securizat codificat în Base64.
  • Pasul B: Se creează un obiect de tip imagine virtuală în memorie (new Image()), având ca sursă string-ul codificat (Data URL): image.src = 'data:image/svg+xml;base64,...'.
  • Pasul C: La încărcarea imaginii virtuale, sistemul instanțiază un element HTML5 <canvas> ascuns în fundal și îi preia contextul de desenare bidimensional (canvas.getContext('2d')). Formele geometrice din SVG sunt astfel redesenate ("blitted") direct pe matricea de pixeli a canvasului.
  • Pasul D: Se apelează metoda nativă a canvasului canvas.toDataURL('image/webp'). Aceasta comprimă instantaneu matricea de pixeli în formatul WebP și returnează un string binar descărcabil, pe care frontend-ul îl atașează unui element temporar de tip ancoră <a> cu atributul download, declanșând descărcarea directă pe laptopul clientului, cu zero latență de rețea.
