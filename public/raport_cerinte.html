Abstract

Proiectul AwA (Actor Awards Visualizer) reprezintă o soluție informatică integrată dedicată procesării, analizei și vizualizării datelor istorice referitoare la performanțele actorilor în cadrul galelor de premiere cinematografică. Documentul de față detaliază cerințele funcționale și non-funcționale ale sistemului, utilizând standardele IEEE 830-1998 și formatul Scholarly HTML. Aplicația pune accent pe utilizarea tehnologiilor Web native, eliminând dependența de framework-uri externe pentru a asigura o performanță optimă și o mentenanță simplificată.

1. Introducere

1.1 Scopul și Obiectivele Documentului

Acest document constituie Specificația Cerințelor Software (SRS - Software Requirements Specification) pentru platforma AwA (Actor Awards Visualizer). Redactat în conformitate cu standardul internațional IEEE 830-1998 și structurat semantic prin formatul Scholarly HTML, scopul acestui raport este de a defini riguros arhitectura funcțională, constrângerile de design și specificațiile tehnice ale sistemului.

Documentul servește ca un contract tehnic și ghid de dezvoltare pentru echipa de inginerie software, asigurând că toate interacțiunile utilizatorilor și fluxurile de date din fundal sunt mapate corect pe cerințele academice. Publicul țintă include evaluatorii de proiect, dezvoltatorii web nativi și auditorii de securitate interesați de sisteme web decuplate.

1.2 Domeniul de Aplicare și Contextul Industrial (Scope)

În industria cinematografică actuală, istoricul și evoluția premiilor obținute de actori (cum sunt cele decernate de Screen Actors Guild - SAG) reprezintă o resursă valoroasă pentru critici, jurnaliști și pasionații de artă digitală. Totuși, majoritatea platformelor existente oferă seturi de date sub formă tabelară rigidă sau text chior, îngreunând identificarea tendințelor istorice sau a ratelor de succes.

Sistemul AwA rezolvă această problemă acționând ca un punct centralizat de analiză asincronă. Aplicația preia seturi masive de date brute din fișiere CSV, le corelează inteligent cu metadate biografice prin API-uri media internaționale și le convertește instantaneu în grafice vectoriale interactive (SVG). Proiectul nu se rezumă la afișarea de date statistice, ci include module complexe de notificare în timp real pentru utilizatorii autentificați, un agregator dinamic de știri bazat pe parsare de fluxuri XML și un panou administrativ securizat de control global pentru managementul bazei de date și al clienților.

1.3 Definiții, Acronime și Abrevieri

  • SRS (Software Requirements Specification): Document formal ce descrie funcționalitățile și performanțele unui sistem software.
  • SVG (Scalable Vector Graphics): Format de imagine vectorială bazat pe XML, utilizat pentru randarea graficelor fără pierderi de rezoluție.
  • API (Application Programming Interface): Set de endpoint-uri HTTP utilizat pentru schimbul asincron de date între sisteme.
  • TMDb (The Movie Database): Serviciu web extern utilizat pentru preluarea biografiilor și imaginilor oficiale ale actorilor.
  • CRUD (Create, Read, Update, Delete): Cele patru operații fundamentale ale persistenței datelor.
  • ACID (Atomicity, Consistency, Isolation, Durability): Set de proprietăți care garantează că tranzacțiile din baza de date sunt procesate în condiții de deplină siguranță.

2. Descriere Generală

2.1 Perspectivele și Arhitectura Macro a Sistemului

Platforma AwA este proiectată ca o aplicație distribuită, bazată pe un model client-server complet decuplat. Aceasta înseamnă că logica de afișare și randare (Frontend) este complet separată de logica de business, persistență și procesare matematică (Backend).

Interfața client rulează ca o aplicație Single Page (SPA) nativă în browser-ul utilizatorului, fiind construită exclusiv în HTML5, CSS3 și JavaScript modern. Comunicarea cu serverul se face asincron prin protocolul HTTPS, trimițând cereri de tip Fetch API și primind înapoi seturi de date structurate exclusiv în format JSON. Backend-ul este un API RESTful dezvoltat în PHP 8 nativ, care interacționează direct cu un motor relațional embedded SQLite 3. Această structură elimină nevoia de framework-uri grele și oferă un control total asupra execuției codului și utilizării memoriei.

2.2 Clase de Utilizatori, Roluri și Matricea de Privilegii

Sistemul identifică trei tipuri distincte de utilizatori umani, fiecare având un nivel diferit de interacțiune, drepturi de acces și comportament în raport cu sistemul de notificări al platformei:

  • Vizitator Anonim (Utilizator Neautentificat):
    Caracteristici: Reprezintă publicul larg care accesează platforma din exterior fără un cont de acces.
    Drepturi: Poate folosi bara de căutare predictivă pentru a găsi actori, poate citi profilurile publice populate din cache-ul local sau TMDb și poate vizualiza și exporta graficele macro native SVG. Nu are acces la zona de știri personalizate, nu poate interacționa cu sistemul de notificări tranzacționale și nu își poate salva preferințele în baza de date.
  • Client (Utilizator Autentificat în Platformă):
    Caracteristici: Deține un set valid de credențiale în tabela users și a fost validat prin cookie-ul de sesiune.
    Drepturi: Beneficiază de un tablou de bord complet personalizat. Are dreptul de a marca actori ca „Favoriți”, acțiune ce declanșează instantaneu o notificare vizuală de tip Toast în interfață și salvează legătura în baza de date. Primește notificări automate în timp real bazate pe parsarea fluxurilor RSS cinematografice și are capacitatea de a genera exporturi personalizate (.svg sau de înaltă rezoluție comprimată .webp) ale datelor din profilul său de consum.
  • Administrator Sistem (Power User):
    Caracteristici: Utilizator cu privilegii depline (Global Control Overlord) autentificat securizat în panoul administrativ.
    Drepturi: Supraveghează și modifică direct starea întregului ecosistem AwA. Execută importuri masive de date prin încărcarea și parsarea de fișiere CSV (folosind tranzacții atomice pentru a asigura integritatea), controlează catalogul de actori prin operații CRUD extinse, auditează și elimină conturile clienților din sistem și gestionează fluxurile externe active de știri RSS cinematografice.

2.3 Mediu de Operare și Constrângeri Tehnice

Platforma este proiectată să funcționeze pe orice server web capabil să ruleze interpretorul PHP 8 (ex: Apache din suita XAMPP) și care are extensia pdo_sqlite activată. La nivel de client, aplicația este optimizată pentru a respecta cu strictețe principiile de Responsive Web Design (RWD).

Interfața este adaptabilă dinamic folosind exclusiv CSS Flexbox și Grid Layout, garantând o afișare corectă și fluidă pe ecrane de telefoane mobile, tablete și monitoare desktop, fără colapsarea elementelor de text sau suprapunerea butoanelor de notificare. Nu se acceptă dependențe de framework-uri CSS (cum ar fi Bootstrap sau Tailwind), asigurând un cod curat, ușor de întreținut și de auditat conform standardelor W3C.

3. Funcționalitățile Sistemului

3.1 Autentificare, Cookie-uri și Persistența Sesiunii (Clienți & Admini)

Platforma implementează un modul robust de gestionare a stării utilizatorilor. La autentificare, serverul validează credențialele și emite un cookie de sesiune criptat. Pentru clienți, acest cookie permite recunoașterea automată la nivel de browser și personalizarea întregii pagini principale (schimbarea elementelor din meniu, deblocarea butoanelor de adăugare la favoriți). Deconectarea distruge complet cookie-ul și token-urile asociate, curățând memoria locală a browserului.

3.2 Modulul de Căutare Asincronă și Managementul Catalogului de Actori

Sistemul utilizează un mecanism hibrid de căutare. Când un utilizator (vizitator sau client) introduce caractere în câmpul de căutare, o cerere asincronă interoghează baza locală SQLite 3 (care joacă rol de cache). Dacă datele nu sunt complete, sistemul apelează în fundal prin cURL API-ul extern TMDb, salvează automat rezultatele local pentru a optimiza apelurile viitoare și randează profilul complet (biografie, imagini oficiale, listă istorică de nominalizări).

3.3 Motorul de Randare SVG și Modulul de Export Multi-Format

Datele agregate privind ratele de câștig, nominalizările repetate și topurile pe categorii de premii sunt transmise sub formă de obiecte structurate JSON către scriptul de frontend. Aici, un motor matematic calculează razele și coordonatele carteziene pentru a desena dinamic elemente vectoriale native <svg>. Utilizatorii autentificați (clienții) pot exporta aceste structuri fie ca fișiere vectoriale pure (.svg), fie transformate prin intermediul unui context Canvas 2D invizibil în imagini de înaltă rezoluție comprimată (.webp).

3.4 Sistemul de Notificări în Timp Real

Aplicația încorporează un sistem dinamic de avertizare și notificare a clienților și administratorilor. Acesta acționează pe două niveluri:

  • Notificări de Sistem (Tranzacționale): Alertează utilizatorul în mod direct când o acțiune a fost finalizată cu succes (ex: „Actorul a fost adăugat la favoriți!”, „Importul fișierului CSV a fost finalizat cu succes!”, „Eroare la autentificare – credențiale invalide!”).
  • Notificări de Conținut: Clienții sunt avertizați vizual printr-un sistem de badges sau mesaje dinamice în momentul în care administratorul aduce modificări catalogului de actori sau când o nouă sursă RSS de știri a fost activată pe platformă.

3.5 Panoul de Control Global (Drepturi Administrative)

Dedicat exclusiv administratorului, acest modul controlează starea întregii platforme. Adminul are la dispoziție instrumente de audit pentru vizualizarea și ștergerea conturilor de clienți, monitorizarea statisticilor privind preferințele acestora (ce actori au fost salvați cel mai des la favoriți), executarea de importuri masive prin parsarea fișierelor CSV și configurarea completă (CRUD) a surselor RSS cinematografice.

4. Motivațiile Designului

Alegerea unei interfețe fluidizate și renunțarea la framework-uri mari au fost decizii strategice bazate pe următoarele argumente:

  • Accesibilitate și Aliniere: Layout-ul organizat prin CSS Grid și Flexbox permite o adaptare naturală la orice ecran. Câmpurile de căutare și butoanele folosesc reguli de aliniere și spațiere interioară (padding) explicite pentru a preveni colapsarea elementelor sau lipirea textului de margini.
  • Viteză de Randare: Eliminarea overhead-ului cauzat de structuri Virtual DOM grele a dăruit o viteză excelentă și un First Contentful Paint extrem de mic.
  • Sustenabilitate: Codul scris în tehnologii web native (Vanilla JS) este mai sigur, ușor de auditat și independent de actualizări ale unor module terțe.

6. Cerințe Non-Funcționale

6.1 Performanță, Timpi de Răspuns și Metricile de Rețea

Deoarece aplicația AwA funcționează ca o platformă de vizualizare în timp real, performanța percepută de clienți este critică pentru reținerea acestora pe pagină. Constrângerile de viteză sunt segmentate astfel:

  • Latența Căutării Predictive (Sub 100ms): Pentru operațiunile de tastare în bara de căutare asincronă, timpul total de răspuns (Round Trip Time - RTT) de la declanșarea evenimentului input în JavaScript până la afișarea dropdown-ului cu sugestii nu trebuie să depășească 100ms. Această performanță este atinsă prin implementarea unei tehnici de de-bouncing de 200ms în frontend (care previne trimiterea de cereri HTTP la fiecare tastă apasată frenetic) și prin utilizarea indecșilor de tip B-Tree pe coloana nominalizat în baza SQLite.
  • Generarea Agregărilor Statistice (Sub 200ms): Execuția interogărilor de numărare și însumare pe tabela nominations (care poate conține zeci de mii de înregistrări istorice) și transmiterea pachetului de date brute JSON către motorul SVG trebuie să fie finalizată în maximum 200ms. Evitarea operațiunilor de tip JOIN grele în fundal și scrierea de interogări curate optimizează acest timp.
  • Eficiența Memoriei Frontend: Scripturile de randare a graficelor vectoriale nu trebuie să cauzeze scurgeri de memorie (memory leaks). Elementele SVG vechi sunt distruse complet din memoria DOM înainte ca o nouă diagramă să fie injectată dinamic.

6.2 Securitate, Imunizare și Managementul Vulnerabilităților Web

Sistemul aplică standardele OWASP Top 10 pentru a asigura o imunizare completă la nivel de design structural („Security by Design”):

  • Imunizare împotriva Injecțiilor (SQLi): Toate interogările executate din scripturile backend ale API-ului folosesc exclusiv obiectul PDO cu parametrizare strictă (Prepared Statements). Variabilele trimise de clienți nu sunt interpretate niciodată ca instrucțiuni executabile, neutralizând complet riscul de SQL Injection.
  • Prevenirea Execuției de Scripturi Malițioase (XSS): Datele obținute asincron din surse externe (biografii din API-ul TMDb sau string-uri din fluxurile RSS XML) sunt considerate implicit compromise și nesigure. La nivel de PHP, acestea sunt filtrate prin htmlspecialchars(), iar la nivel de frontend sunt introduse în pagină exclusiv prin proprietatea nativă textContent, blocând orice tentativă de Cross-Site Scripting.
  • Managementul Securizat al Parolelor: Platforma respinge stocarea parolelor în clar sau sub formă de hash-uri slabe (cum ar fi MD5 sau SHA1). Se utilizează funcția nativă PHP password_hash() cu algoritmul autoreglabil BCRYPT, aplicând un factor de cost computațional ridicat (cost => 12) pentru a face atacurile de tip brute-force sau rainbow tables imposibile din punct de vedere matematic.
  • Securitatea Sesiunilor Client: Identificatorul PHPSESSID transmis prin cookie folosește directivele directivele HttpOnly (care oprește furtul sesiunii prin console JavaScript) și SameSite=Strict (care oprește atacurile de tip Cross-Site Request Forgery - CSRF).

6.3 Portabilitate, Scalabilitate și Independență de Mediu

Un criteriu non-funcțional cheie în arhitectura AwA este eliminarea fricțiunilor de instalare și configurare (Zero-Configuration Deployment).

  • Persistență Autonomă pe Disc: Utilizarea motorului relațional embedded SQLite 3 implică faptul că întreaga bază de date, cu utilizatori, preferințe, configurări RSS și nominalizări, rezidă într-un singur fișier fizic (data/awa.db). Aplicația este complet portabilă: nu necesită instalarea, pornirea, securizarea sau configurarea unui server de baze de date mamut independent (fără dependențe de MySQL, MariaDB sau PostgreSQL).
  • Portabilitatea Codului Sursă: Structura de directoare este organizată relativ. Proiectul poate fi mutat prin simplu copy-paste din directorul htdocs de pe un laptop de dezvoltare pe un server de producție Linux sau cloud, funcționând instantaneu atât timp cât interpretorul core PHP 8 este activ.
